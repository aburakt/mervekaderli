# Çok dillilik (isteğe bağlı)

Template tek dillidir (TR). İkinci dil gerektiğinde site sıfırdan başlamaz: PB tarafında dil korumaları hazırdır (core), sitede yol ve hreflang yardımcıları hazırdır (başlangıç dosyası). Tek dilli site bunlardan hiçbir şey ödemez: hook kaydedilmez, şema değişmez, build çıktısı aynıdır.

| Parça | Nerede | Core mu |
|---|---|---|
| Dil korumaları (dil başına tek kayıt, çeviri grubu, hazır sayfalar, ayrılmış adresler) | `pb/pb_hooks/lib/i18n.js`, `pb/pb_hooks/i18n.pb.js` | Evet; ayar `site.js` `LANG`'da, tek dilde etkisiz |
| Kararların testi ve gerçek PB'de iki dil/tek dil denemesi | `tests/i18n-hooks.test.ts` | Evet |
| Dil listesi, yollar, hreflang, dil değiştirici, build doğrulamaları | `site/src/lib/i18n.ts` | Hayır (siteye ait; dil listesi ve yol şekli siteye özel) |
| `site.js` ile eşitlik ve yardımcı testleri | `tests/i18n.test.ts` | Hayır |
| `lang`/`alternates` özellikleri, `og:locale`, `<link rel="alternate" hreflang>` | `layouts/Base.astro`, `components/Head.astro` | Hayır |
| Sitemap hreflang | `site/astro.config.mjs` (`LANGS` birden çoksa kendiliğinden) | Hayır |

## Önce karar: hafif mi, tam mı?

- **Hafif** (idealist `/en/` gibi): ikinci dilde tek bir özet sayfa. Şemaya `lang` eklenmez; sabit sayfa `pages` koleksiyonunda kendi kaydıdır (`RULES` ile `noCreate/noDelete/alwaysPublished`). Bu rehberden yalnız 2 (ayar), 5 (rota) ve 6 (hreflang) adımları gerekir; `LANG.rules` boş kalır, PB'de dil hook'u çalışmaz. Sayfa çiftine `sameInAll("/")` ile hreflang verilir.
- **Tam** (expertup gibi): her içerik kaydı dile göre ayrıdır ve çevirileri `translation_group` ile eşleşir. Aşağıdaki bütün adımlar.

## Açma listesi (tam)

### 1. Şema: yeni migration

Var olan migration düzenlenmez; yeni dosya eklenir. Dil alanı `select` (panelde liste), çeviri grubu `text`. Mevcut kayıtlar varsayılan dile geçer, grup kodu adresten dolar.

```js
/// <reference path="../pb_data/types.d.ts" />

// İkinci dil: settings ve posts kayıtlarına dil, posts'a çeviri grubu. Mevcut kayıtlar varsayılan dile (tr) geçer.
migrate((app) => {
  const LANGS = ["tr", "en"]
  const DEFAULT = "tr"
  const LANG_HELP = "Kaydın dili. Her dilin kaydı ayrıdır; Türkçe kayıt sitede öneksiz, İngilizce /en/ altında görünür."
  const GROUP_HELP = "Çeviri eşleştirme kodu: bir kaydın Türkçesi ve İngilizcesi aynı kodu taşır (ör. hakkimizda). Boş bırakırsanız adresten (slug) doldurulur; çeviriyi açarken aynı kodu yazın."
  for (const name of ["settings", "posts"]) {
    const c = app.findCollectionByNameOrId(name)
    c.fields.add(new SelectField({ name: "lang", required: true, maxSelect: 1, values: LANGS, help: LANG_HELP }))
    if (name !== "settings") c.fields.add(new TextField({ name: "translation_group", max: 120, pattern: "^[a-z0-9-]*$", help: GROUP_HELP }))
    app.save(c)
    for (const r of app.findAllRecords(name)) {
      r.set("lang", DEFAULT)
      if (name !== "settings") r.set("translation_group", r.getString("slug"))
      app.saveNoValidate(r)
    }
  }
}, (app) => {
  for (const name of ["settings", "posts"]) {
    const c = app.findCollectionByNameOrId(name)
    c.fields.removeByName("lang")
    c.fields.removeByName("translation_group")
    app.save(c)
  }
})
```

- Her yeni alanda Türkçe `help` (test ölçer). API kuralları değişmez (`published = true` aynen kalır).
- Adres (slug) core `protect.js`'te koleksiyon içinde benzersizdir, dilden bağımsız: TR ve EN kayıt aynı adresi taşıyamaz (`iletisim` / `contact` gibi farklı yazılır). Bu bilerek böyledir; ayrı dil başına benzersizlik gerekmez.
- Sunucuya migration ve hook'lar aynı anda gider (dil kuralları `lang` alanı olmayan kayıtları reddeder).

### 2. Ayar: iki yerde, aynı değerler (test ölçer)

`pb/pb_hooks/site.js`:

```js
RULES: {
  // singleton kaldırılır: dil başına tek kayıt LANG.rules.settings.perLang ile sağlanır (test ölçer)
  settings: { label: "Site Ayarları", noDelete: true, deleteHint: "alanları düzenleyin." },
  posts: { slugFrom: "title", locked: ["slug"] },
},
LANG: {
  langs: ["tr", "en"],
  default: "tr",
  reserved: ["tr", "en", "api", "_astro", "yazilar"],
  rules: {
    settings: { label: "Site Ayarları", perLang: true },
    posts: { label: "Yazılar", grouped: true },
    // sabit sayfalar varsa: pages: { label: "Sayfalar", grouped: true, fixed: ["home", "contact"], alwaysPublished: ["home"] },
  },
},
```

`site/src/lib/i18n.ts`:

```ts
export const LANGS = ["tr", "en"] as const
export const DEFAULT_LANG: Lang = "tr"
export const RESERVED_SLUGS = ["tr", "en", "api", "_astro", "yazilar"] as const
export const LOCALES: Record<Lang, { og: string; hreflang: string; name: string }> = {
  tr: { og: "tr_TR", hreflang: "tr", name: "Türkçe" },
  en: { og: "en_US", hreflang: "en", name: "English" },
}
```

- `reserved`: her dil kodu ve kökteki her sabit yol (`/yazilar/`, `/api/`, `/_astro/`); kökte `[slug]` rotası olan sitede bir kayıt bunlarla çakışamaz. Yeni kök yolu eklenince iki listeye de yazılır.
- Kural alanlarının anlamı `pb/pb_hooks/lib/i18n.js` başında: `perLang` (dil başına tek kayıt, silinemez, dili değişmez), `grouped` (aynı grupta aynı dil bir kez, aynı dilde aynı adres bir kez; boş grup adresten dolar), `fixed` (silinemeyen, dili/adresi/grubu kilitli hazır gruplar), `alwaysPublished`.

### 3. Panel etiketleri

`pb/pb_hooks/panel/labels.json` `fields`: `"translation_group": "Çeviri eşleştirme kodu"` (`lang` ortak sözlükte "Dil"). Yeni koleksiyon açıldıysa `collections`'a da (test ölçer). Müşteri rehberine (`docs/panel-rehberi.md`) bir paragraf: çeviri açarken aynı kodu yazmak, ayarların her dilde bir kaydı olduğu.

### 4. İçerik yükleme ve fixture

- `lib/types.ts`: kayıtlara `lang` ve `translation_group`; `Site.settings` dil başına (`Record<Lang, Settings>`).
- `lib/pb-loader.ts`: `lang` ve `translation_group` alanlarını taşır; `assertSlugs(posts, "posts")` ve `assertGroups(posts, "posts")` ile bozuk veride build kırılır (PB de aynı kayıtları reddeder; bu ikinci kilit).
- `site/src/data/content.json` ve `scripts/seed.ts`: her kayda `lang`, eşlere aynı `translation_group`. PB/fixture paritesi (`bun run verify`) iki dilde de aynı sayfaları ister.
- Sayfalar `ofLang(posts, lang)` ile süzer.

### 5. Rotalar

Varsayılan dil öneksiz, diğerleri `/<dil>/`. Astro'nun i18n yönlendirmesi kullanılmaz; dosyalar açıkça yazılır:

```
site/src/pages/index.astro             -> TR ana sayfa      <Home lang="tr" />
site/src/pages/en/index.astro          -> EN ana sayfa      <Home lang="en" />
site/src/pages/yazilar/[slug].astro    -> TR yazılar        getStaticPaths: ofLang(posts, "tr")
site/src/pages/en/yazilar/[slug].astro -> EN yazılar        getStaticPaths: ofLang(posts, "en")
```

Sayfa gövdesi bir görünüm bileşenine (`views/Home.astro`) taşınır, iki rota dosyası yalnız dil verir. Yollar elle yazılmaz: `localePath(lang, "/yazilar/x/")`. Arayüz metinleri (menü, "Tüm yazılar") küçük bir sözlükte (`const UI: Record<Lang, …>`) tutulur.

### 6. hreflang, dil değiştirici, sitemap

```astro
---
const alternates = alternatesFor(post, posts, (p) => localePath(p.lang, `/yazilar/${p.slug}/`))
---
<Base lang={lang} alternates={alternates} title={post.title} path={localePath(lang, `/yazilar/${post.slug}/`)}>
```

- `Head.astro` `hreflangLinks(alternates)` ile eşleri ve `x-default`'u yazar; çevirisi olmayan sayfada hiçbir şey yazmaz (ölü hreflang yok). `og:locale` `LOCALES[lang].og`.
- Sabit yollu sayfa (ana sayfa, liste): `alternates={sameInAll("/")}`.
- Dil değiştirici: `switchLinks(lang, alternates)`; eşi olmayan dilde o dilin ana sayfasına gider, 404'e değil. Bağlantıya `hreflang` ve `lang` özniteliği.
- Sitemap: `astro.config.mjs` `LANGS` birden çoksa `@astrojs/sitemap` `i18n` ayarını kendisi ekler (eş adresler `xhtml:link` olarak).

### 7. Kontroller

`site.config.ts`:

- Ana sayfa kontrolündeki `hasNot: ["hreflang"]` kaldırılır; `has`'a `'hreflang="en"'` ve `'hreflang="x-default"'`.
- `/en/` ve bir EN yazı için kontrol (`<html lang="en"`).
- `testSeed`/`testChecks`: çevirisi olmayan bir yazı tohumlanır; sayfasında `hreflang` olmadığı, dil değiştiricinin `/en/`'e gittiği ölçülür.

Bitti: `bunx oxlint && bun run check && bun test && bun run verify`. `tests/i18n.test.ts` iki dosyanın eşitliğini ve yardımcıları, `tests/i18n-hooks.test.ts` PB korumalarını ölçer.

## Neden PB tarafı core, site tarafı değil

- PB korumaları (`lib/i18n.js`, `i18n.pb.js`) her sitede aynı mantıktır ve ayarı `site.js`'ten okur; tek dilde hook bile kaydetmez, şema istemez. Düzeltme bir kez template'te yapılır, `core:sync` ile bütün çok dilli sitelere gider.
- `site/src/lib/i18n.ts` dil listesini ve sitenin yol şeklini taşır (expertup'ta `/project/`, burada `/yazilar/`); her sitede farklıdır, core olsa her senkronda siteninkini ezerdi. Bu yüzden başlangıç dosyasıdır; yardımcılar `I18nConfig` alır, ayar dosyanın başındadır.
- PB hook dosyaları sırasız yüklenir; `lib/i18n.js` slug'ı denetlemeden önce core panel korumasını (`protect.js`, slug üretimi) kendisi çağırır, sıra fark etmez.
